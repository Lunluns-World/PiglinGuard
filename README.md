# PiglinGuard

Paper 插件。殭屍化豬布林從**主世界**穿過地獄傳送門要進**地獄**時，如果牠來自傳送門型金磚場，就直接移除，不讓牠過去。

伺服器的公共金磚場會不斷把殭屍化豬布林推進傳送門，地獄那一側沒有東西會殺牠們，於是越堆越多。曾經有一份 spark 報告在地獄側看到 11,662 隻殭屍化豬布林和 2,940 個掉落物，光是生物運算就佔了主執行緒約 8.7%。這些豬布林對金磚場的產量沒有任何貢獻，移除牠們不會讓玩家少拿到東西。

## 對一般玩家的影響

只有一件事會變：**符合條件的殭屍化豬布林穿過主世界的傳送門時，會直接消失，不會出現在地獄。**

其他一切都和原版相同：

- 玩家、其他生物、掉落物穿過傳送門都不受影響。
- 從地獄回主世界、去終界都不受影響。
- 有命名、被拴繩拴著、正在騎乘或載著其他實體的殭屍化豬布林永遠不會被移除。
- 一般玩家的傳送門不受影響：自動偵測預設只處理金磚場會產生的豬布林（從傳送門生成，或豬布林被打時叫來的援軍），而且附近的傳送門方塊數量必須達到門檻。原版單一個傳送門最多 441 格，遠低於預設門檻 1000。
- 金磚場的產出不受影響：豬布林在主世界被殺掉的流程完全沒變，只是不會再有多出來的豬布林跑進地獄。

## 安裝

1. 需要 Paper 1.21.8 以上（也可以用在 Folia），Java 21 以上。
2. 執行 `./gradlew build`，把 `build/libs/PiglinGuard-<版本>.jar` 放進伺服器的 `plugins/`。
3. 啟動伺服器。Kotlin 標準函式庫會由 Paper 自動下載（寫在 `plugin.yml` 的 `libraries:`），不需要另外安裝。
4. 第一次啟動會產生 `plugins/PiglinGuard/config.yml` 和 `areas.yml`。

## 判斷流程

每次殭屍化豬布林要穿過傳送門，依序檢查，第一個符合的就是結果：

1. 以下情況一律不處理：不是殭屍化豬布林、不是主世界 → 地獄、世界不在 `worlds` 裡、有自訂名稱、被拴繩拴著、正在騎乘或載著其他實體。
2. 傳送門位置在**白名單**區域內 → 不處理（`IGNORE_WHITELIST`）。
3. 傳送門位置在**黑名單**區域內 → 移除（`REMOVE_BLACKLIST`），不看密度，也不看生成原因。
4. 自動偵測（`auto-detect.enabled: true` 時）：
   - `require-portal-spawn: true` 時，豬布林的生成原因必須在 `farm-spawn-reasons` 裡（預設是 `NETHER_PORTAL` 從傳送門生成、`REINFORCEMENTS` 被打時叫來的援軍）；
   - 傳送門附近 `radius` 格內（水平方向，整個世界高度）的地獄傳送門方塊數量 ≥ `threshold`；
   - 兩者都成立 → 移除（`REMOVE_AUTO`）。
5. 其他情況 → 不處理，照原版行為。

移除時會取消這次傳送，並把豬布林從世界中移除。只取消傳送是不夠的：豬布林會卡在傳送門方塊裡每 tick 重試，還可能擋住金磚場的水流。

## 指令

主指令 `/piglinguard`，別名 `/pg`。權限 `piglinguard.admin`（預設只有 OP 有）。支援 Tab 補全。

| 指令 | 說明 |
| --- | --- |
| `/pg wl add <名稱> <半徑>` | 以你腳下為中心建立白名單區域，水平半徑 `<半徑>` 格，涵蓋整個世界高度 |
| `/pg wl pos1`、`/pg wl pos2` | 記錄你目前所在的方塊為角落（每位玩家各自記錄，只存在記憶體中，`wl` 和 `bl` 共用） |
| `/pg wl add <名稱>` | 不加半徑時，用 pos1 和 pos2 圍出的方塊建立區域 |
| `/pg wl remove <名稱>` | 刪除白名單區域 |
| `/pg bl ...` | 黑名單，用法同上 |
| `/pg list` | 列出所有區域（名稱、世界、範圍） |
| `/pg scan` | 顯示你目前位置的傳送門密度（統計了幾個區塊、總數）、是否在白名單或黑名單內，以及「傳送門生成的殭屍化豬布林在這裡會怎樣」 |
| `/pg stats` | 啟動以來黑名單移除、自動偵測移除、白名單放行的次數，以及移除最多的前 5 個區塊 |
| `/pg reload` | 重新載入 `config.yml` 和 `areas.yml` |

區域名稱只能使用英文字母、數字、底線和減號，最多 32 字。同名的區域會被覆蓋更新。

## 設定 `config.yml`

```yaml
worlds: [world]              # 要處理的世界（主世界那一側）
auto-detect:
  enabled: true              # 是否啟用自動偵測
  radius: 24                 # 水平半徑（格）
  threshold: 1000            # 門檻。原版單一傳送門最多 21x21 = 441 格，所以要 > 441
  require-portal-spawn: true # 只處理生成原因在 farm-spawn-reasons 裡的豬布林
  farm-spawn-reasons: [NETHER_PORTAL, REINFORCEMENTS]  # 算作「金磚場產生的」生成原因
  cache-ttl-minutes: 10      # 傳送門數量快取的保險過期時間
log-removals: false          # 開啟後每次移除都會記錄到後台（世界、座標、原因）
```

- 缺少的設定會自動補上預設值。
- 格式錯誤的值會在後台顯示警告，並改用預設值，插件不會因此停止。
- `threshold` ≤ 441 會顯示警告，但仍然照你設定的值使用。

## 區域 `areas.yml`

```yaml
whitelist:
  spawn_portal:
    world: world
    min: [-20, -64, -20]
    max: [20, 319, 20]
blacklist:
  gold_farm:
    world: world
    min: [1000, -64, 1000]
    max: [1100, 319, 1100]
```

範圍包含 `min` 和 `max` 兩端的方塊。一般用指令建立就好；手動修改後記得執行 `/pg reload`。

## 怎麼校正門檻

1. 站到金磚場的傳送門旁邊，執行 `/pg scan`。如果顯示「有 N 個區塊還沒算好」，等幾秒後再掃一次。記下密度 A。
2. 站到一般玩家會使用的傳送門旁邊（例如主城的傳送門），執行 `/pg scan`。記下密度 B。
3. 把 `threshold` 設在 B 和 A 之間，最好明顯高於 B，例如取 B 和 A 的中間值，並且一定要 > 441。
4. `/pg reload` 後，再到兩個地方各掃一次，確認金磚場顯示「會被移除」，一般傳送門顯示「不會被處理」。
5. 如果金磚場的傳送門數量不夠多、很難和一般傳送門分開，直接用 `/pg bl add <名稱> <半徑>` 把金磚場設成黑名單最可靠。反過來，有誤判的地方可以用 `/pg wl add` 排除。

`radius` 調大時，算進來的區塊會變多，A 和 B 都會跟著變大，記得重新校正。

## 已知限制

- **密度是以區塊為單位計算的。** 計算時會把「和半徑範圍有重疊的所有區塊」整個加進來，所以實際統計的範圍會比 `radius` 大，最多每邊多出 15 格。精度是區塊級，不是方塊級。
- 只統計**已載入的區塊**。還沒算好的區塊先當作 0，並安排背景計算，所以剛載入的地方第一次可能會偏低，稍後就會正確。
- 傳送門建立或破壞後，大約 1 秒（20 tick）後才會重新計算該區塊，另外每 `cache-ttl-minutes` 分鐘也會重新計算一次作為保險。
- 用 `/fill`、WorldEdit 之類的工具直接放置傳送門方塊時不會觸發「傳送門建立」事件，可能要等區塊重新載入、附近方塊更新或快取過期後才會算進去。
- `require-portal-spawn` 依靠 Paper 記錄的生成原因。用指令或生怪蛋產生的豬布林不算金磚場產生的。`/pg stats` 會列出被略過的豬布林實際的生成原因，如果金磚場還有別的生成原因，可以加進 `farm-spawn-reasons`。
- 只處理「主世界 → 地獄」方向，從地獄回主世界的不會被處理。
- Folia：程式依照 Folia 的執行緒規則撰寫（沒有使用 `Bukkit.getScheduler()`，區塊快照在所屬區域執行緒上取得），但目前只在 Paper 1.21.8 上實際測試過。

## 開發

```bash
./gradlew build      # 編譯並執行單元測試
./gradlew runServer  # 用 run-paper 啟動 Paper 1.21.8 測試伺服器（第一次需在 run/eula.txt 同意 EULA）
```

### 自動建置與發布

- 推到 `main` 或開 PR 時，GitHub Actions 會自動建置並跑測試，jar 可以在該次執行的 Artifacts 下載。
- 要發布新版本：先把 `build.gradle.kts` 的 `version` 改成新版本並推上去，再推一個同名的 tag，例如：

  ```bash
  git tag v1.0.1 && git push origin v1.0.1
  ```

  Actions 會建置後建立 GitHub Release，並附上 jar。tag 和 `version` 不一致時會直接失敗，不會發布。
